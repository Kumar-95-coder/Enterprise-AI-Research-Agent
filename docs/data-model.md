# Data Model

16 tables, SQLAlchemy models in `backend/app/models.py`, versioned via Alembic (`backend/migrations/`).

## Entity relationship summary

```
research_jobs 1---* research_subquestions
research_jobs 1---1 research_plans
research_jobs *---* sources          (via job_sources: tracks new-vs-reused per job)
research_jobs 1---* findings
research_jobs 1---* claims
research_jobs 1---* contradictions
research_jobs 1---* conclusions
research_jobs 1---* research_runs    (pipeline stage audit log)

sources       1---* findings
findings      *---1 claims           (primary claim, findings.claim_id)
claims        *---* findings         (claim_findings: explicit stance = supporting/contradicting/neutral)
claims        1---* contradictions   (as claim_a or claim_b)
findings      *---* entities         (findings.entities: JSON list of entity ids)
entities      *---* entities         (via relationships: source_entity -> relation_type -> target_entity)
conclusions   *---* claims           (conclusions.supporting_claim_ids: JSON list)
conclusions   1---* citations
```

## Deliberate simplifications (and why)

- **`documents` merged into `sources`.** The assignment lists both; in this implementation each source maps 1:1 to one retrieved page/document, so a separate `documents` table would just duplicate `sources` with no independent rows. A production system ingesting multi-page PDFs or multi-section reports would split a source into several `documents` (one row per page/section) while keeping the citation-level metadata on `sources`.
- **`citations` is materialized, not purely computed.** The Claim -> Evidence -> Source chain already implies citations; `citations` is a separate table anyway (populated during the VALIDATING pipeline stage) because the assignment explicitly requires citations to be *preserved and queryable* as their own artifact, not just re-derivable by joining four tables every time.
- **Entities and sources are globally deduplicated, not per-job.** A `Source` is unique by normalized URL across the *entire* knowledge base; `job_sources` is the join table that tracks which jobs actually used which source, and whether that source was newly retrieved or reused for that specific job. This is the concrete mechanism behind "knowledge reuse."
- **Relationships are entity-to-entity only.** `Source -> supports -> Claim` and `Source -> contradicts -> Claim` (also listed in the assignment's example relationship set) are already fully expressed by `claim_findings.stance` plus `findings.source_id` — adding a second, redundant relationship table for the same fact would just be two representations of one truth that could drift out of sync.

## Evidence quality scoring (documented, not "arbitrary precision as fact")

`Source.quality_score` (0–1) is a transparent weighted heuristic, not a statistically validated score:

```
base = source_type_weight   # government/academic/standards: 0.90-0.95
                             # industry_report/technical_documentation: 0.70-0.75
                             # news_business: 0.60, generic web: 0.50
+ 0.05 if a publication_date is known
+ 0.03 if an author/attribution is known
```

`Finding.confidence` (0–1) combines a base of 0.4, +0.3 if the sentence contains a digit (a rough proxy for "specific, checkable claim" vs. vague assertion), +0.3 × the source's quality_score. `Finding.evidence_strength` (strong/moderate/weak) is a bucketed view of the same confidence score. Both are cheap, explainable heuristics intended to be legible and debuggable, not a validated scoring model — this is stated plainly in the UI copy as well, not just in this doc.

## Indexes and constraints actually in the migration

- Unique: `sources.url`, `sources.normalized_url` (deduplication), `(job_id, source_id)` on `job_sources`, `(claim_id, finding_id)` on `claim_findings`, `(name, entity_type)` on `entities`, `(object_type, object_id)` on `knowledge_vectors`.
- Indexes: `research_jobs.status`, `research_jobs.created_at`, every foreign key column referenced in a hot query path (`findings.research_job_id`, `findings.sub_question_id`, `findings.source_id`, `findings.claim_id`, `sources.normalized_url`, `sources.content_hash`, etc.) — see the autogenerated migration `backend/migrations/versions/*_initial_schema.py` for the exact list.
